## ⁦7.1⁩ הבעיה: הכתובת הפרטית לא יוצאת

בפרק ⁦2⁩ למדנו שכל הרשת שלנו בטווח **פרטי** – ⁦10.0.0.0/8⁩ – ושנתבי האינטרנט **לא מעבירים** כתובות כאלה. מיליוני ארגונים משתמשים ב-⁦10.1.16.40⁩ בו זמנית. אם מחשב כזה ישלח חבילה לגוגל עם כתובת המקור ⁦10.1.16.40⁩ – גוגל תענה... לאן? ל-⁦10.1.16.40⁩ – שיש כמוהו מיליון. התשובה לא תחזור לעולם.

הפתרון: בדרך החוצה, הנתב **מחליף** את הכתובת הפרטית ב**כתובת ציבורית** – כזאת שיש רק אחת ממנה בעולם. וכשהתשובה חוזרת, הוא מחליף בחזרה. זה **⁦NAT (Network Address Translation)**.⁩

<div dir="ltr" align="left">

```
   PC 10.1.16.40                  EDGE ROUTER (NAT)                    google.com
        |                        inside | outside                          |
        |  src 10.1.16.40 ------------->|                                  |
        |  dst 142.250.1.1              |  src 200.100.1.10 -------------->|
        |                               |  dst 142.250.1.1                 |
        |                               |                                  |
        |                               |<-- src 142.250.1.1 --------------|
        |<---- src 142.250.1.1 ---------|    dst 200.100.1.10              |
        |      dst 10.1.16.40           |                                  |
                                        |
                          NAT TABLE:    inside 10.1.16.40  <->  outside 200.100.1.10
```

</div>

**אוצר המילים של ⁦NAT⁩** (נשאל בבחינה):

| מונח | פירוש |
|---|---|
| **⁦Inside Local⁩** | הכתובת הפרטית של המחשב, כפי שהיא בפנים – ⁦10.1.16.40⁩ |
| **⁦Inside Global⁩** | הכתובת הציבורית שהמחשב "נראה" בה מבחוץ – ⁦200.100.1.10⁩ |
| **⁦Outside Global⁩** | הכתובת האמיתית של היעד באינטרנט – ⁦142.250.1.1⁩ |

## ⁦7.2⁩ שלושת סוגי ה-⁦NAT⁩ – ובפרויקט, אחד לכל סניף

דרישה ⁦10⁩ בפרויקט: "⁦NAT⁩ על כל הסניפים – בסניף אחד דינמי, באחד סטטי, ובאחרון ⁦Overload."⁩ שלושה סוגים, שלוש בעיות שונות.

### א. ⁦NAT⁩ סטטי – כתובת פרטית אחת ↔ כתובת ציבורית אחת, קבוע

**הבעיה שהוא פותר:** יש לנו שרת ⁦WEB⁩ פנימי ב-⁦10.1.200.80⁩, ואנשים **מבחוץ** צריכים להגיע אליו. תעבורה **נכנסת**. הנתב חייב לדעת מראש: "מי שפונה ל-⁦200.100.1.80⁩ – תעביר ל-⁦10.1.200.80".⁩ תרגום קבוע, שני הכיוונים.

```
Router(config)# ip nat inside source static 10.1.200.80 200.100.1.80
Router(config)# interface Gi0/0
Router(config-if)# ip nat inside
Router(config)# interface Gi0/1
Router(config-if)# ip nat outside
```

| שורה | למה |
|---|---|
| `⁦ip nat inside source static A B⁩` | "כתובת פנימית ⁦A⁩ = כתובת ציבורית ⁦B⁩, תמיד" |
| `⁦ip nat inside⁩` / `⁦ip nat outside⁩` | **חובה על הממשקים.** ⁦NAT⁩ צריך לדעת איזה צד "פנים" ואיזה "חוץ". בלי זה – שום תרגום. הטעות הכי נפוצה. |

**בפרויקט:** תל אביב – כדי לפרסם את שרת ה-⁦WEB⁩ ב-⁦DMZ⁩ (דרישה ⁦22.12).⁩

### ב. ⁦NAT⁩ דינמי – מאגר של כתובות ציבוריות, מוקצות לפי הצורך

**הבעיה:** ⁦200⁩ מחשבים גולשים, יש לנו ⁦20⁩ כתובות ציבוריות. כל מחשב שיוצא מקבל כתובת פנויה מהמאגר, ומחזיר אותה כשסיים.

```
Router(config)# ip nat pool HAIFA-POOL 200.100.2.10 200.100.2.29 netmask 255.255.255.0
Router(config)# access-list 1 permit 10.2.0.0 0.0.255.255
Router(config)# ip nat inside source list 1 pool HAIFA-POOL
```

| שורה | למה |
|---|---|
| `⁦ip nat pool⁩` | ⁦20⁩ כתובות ציבוריות, .⁦10⁩ עד .⁦29⁩ |
| `⁦access-list 1 permit ...⁩` | **מי** מותר לו לתרגם – כל ⁦10.2.x.x (wildcard⁩ – פרק ⁦2)⁩ |
| `⁦ip nat inside source list 1 pool⁩` | "מי שעובר ב-⁦ACL 1⁩ – קח כתובת מהמאגר" |

**המגבלה:** כתובת אחת למחשב אחד בו זמנית. המחשב ה-⁦21⁩ מחכה. **בפרויקט:** חיפה.

### ג. ⁦NAT Overload (PAT)⁩ – כולם דרך כתובת אחת

**הבעיה:** יש לנו כתובת ציבורית **אחת** ו-⁦300⁩ מחשבים. הפתרון הגאוני: להבדיל ביניהם לפי **מספר הפורט**. כל מחשב מקבל את אותה כתובת ציבורית אבל פורט מקור שונה:

<div dir="ltr" align="left">

```
PC-A  10.1.16.40 : 51000  ---->  200.100.3.1 : 51000  ---->  google
PC-B  10.1.16.41 : 51000  ---->  200.100.3.1 : 51001  ---->  google   (port changed - was taken)
PC-C  10.1.16.42 : 52200  ---->  200.100.3.1 : 52200  ---->  google

NAT TABLE (PAT):
  10.1.16.40:51000  <->  200.100.3.1:51000
  10.1.16.41:51000  <->  200.100.3.1:51001
  10.1.16.42:52200  <->  200.100.3.1:52200

  ~ 64,000 ports  ->  ~ 64,000 simultaneous connections through ONE public address.
```

</div>

```
Router(config)# access-list 1 permit 10.3.0.0 0.0.255.255
Router(config)# ip nat inside source list 1 interface Gi0/1 overload
```

`⁦interface Gi0/1⁩` – "השתמש בכתובת של הממשק היוצא" (אין מאגר). `⁦overload⁩` – "ותבדיל לפי פורטים". **זה מה שהנתב בבית שלכם עושה.** **בפרויקט:** באר שבע.

| | סטטי | דינמי | ⁦Overload (PAT)⁩ |
|---|---|---|---|
| **יחס** | ⁦1:1⁩ קבוע | ⁦1:1⁩ זמני ממאגר | רבים:⁦1⁩ לפי פורט |
| **כיוון** | שני הכיוונים | פנים → חוץ | פנים → חוץ |
| **בשביל** | שרת שצריך להיות נגיש מבחוץ | כמה מחשבים, כמה כתובות | הכול דרך כתובת אחת |
| **בפרויקט** | תל אביב (⁦WEB)⁩ | חיפה | באר שבע |

> 🔐 **⁦NAT⁩ הוא לא אבטחה – אבל הוא עוזר**
>
> תוצאת לוואי: מבחוץ אי אפשר לפנות **יזום** למחשב פנימי ב-⁦PAT⁩, כי אין לו שורה בטבלה עד שהוא יוצא ראשון. זה נראה כמו חומת אש. **זה לא.** חומת אש בודקת מדיניות; ⁦NAT⁩ רק מתרגם. תוקף שמצא דרך אחרת פנימה – ⁦NAT⁩ לא יעצור אותו. חומות אש אמיתיות – חלק ⁦2⁩, פרק ⁦4.⁩

## ⁦7.3⁩ מה זה ⁦ISP⁩, ומה זה ⁦AS⁩

**ספק אינטרנט (⁦ISP⁩ – ⁦Internet Service Provider)⁩** הוא מי שמחבר אתכם לעולם. בפרויקט בונים ⁦ISP⁩ משלנו: נתב, שרת ⁦DNS⁩, שני שרתי ⁦WEB⁩, וחיבור לכל הסניפים דרך מודם ⁦DSL.⁩

וכאן נכנס המושג שעליו בנוי האינטרנט כולו: **מערכת אוטונומית (⁦Autonomous System, AS)⁩** – אוסף רשתות תחת **ניהול אחד**, עם **מדיניות ניתוב אחת**. הארגון שלנו הוא ⁦AS.⁩ הספק הוא ⁦AS.⁩ גוגל היא ⁦AS.⁩ לכל ⁦AS⁩ יש מספר: **⁦ASN**.⁩ האינטרנט = עשרות אלפי ⁦AS⁩-ים שמדברים זה עם זה.

**בתוך** ⁦AS⁩ – פרוטוקול פנימי: ⁦OSPF⁩ או ⁦EIGRP⁩ (פרק ⁦6).⁩ אלה **⁦IGP⁩ – ⁦Interior Gateway Protocol**.⁩ **בין** ⁦AS⁩-ים – פרוטוקול חיצוני: **⁦EGP⁩ – ⁦Exterior Gateway Protocol**.⁩ והיחיד שבשימוש בעולם הוא **⁦BGP**.⁩

| | ⁦IGP (OSPF, EIGRP) | EGP (BGP)⁩ |
|---|---|---|
| **איפה** | בתוך ארגון | בין ארגונים / ספקים |
| **מה חשוב** | הדרך **הכי מהירה** | הדרך **המותרת לפי מדיניות** (עסקית, חוזית) |
| **סומך על** | כל הנתבים בארגון | רק על השכן הישיר – ובזהירות |
| **מטריקה** | עלות / רוחב | **תכונות (⁦Attributes)⁩** |

## ⁦7.4 BGP⁩ – היסודות

**⁦BGP (Border Gateway Protocol)⁩** – הפרוטוקול של האינטרנט. ⁦Path Vector⁩: כל נתיב נושא את **רשימת ה-⁦AS⁩-ים** שהוא עבר דרכם (⁦AS-PATH).⁩ מזה נובע:

- **מניעת לולאות:** נתב שרואה את ה-⁦ASN⁩ **שלו** ב-⁦AS-PATH⁩ של נתיב – זורק אותו. הנתיב כבר עבר דרכי. (זו התשובה לשאלה "איזה ⁦attribute⁩ מונע לולאות?")
- **מדיניות:** ספק יכול להעדיף נתיב דרך שותף עסקי ולא דרך מתחרה, גם אם המתחרה קרוב יותר.

⁦BGP⁩ לא משתמש ב-⁦multicast.⁩ השכנים מוגדרים **ידנית**, ומדברים ב-**⁦TCP⁩ פורט ⁦179**.⁩ אין "גילוי" – אתה אומר לנתב בדיוק עם מי לדבר.

| | ⁦eBGP | iBGP⁩ |
|---|---|---|
| **בין** | שני ⁦AS⁩-ים **שונים** | שני נתבים **באותו** ⁦AS⁩ |
| **⁦AD** | **20** | **200⁩** |
| **טיפוסי** | הסניף ↔ הספק | שני נתבי קצה של אותו ארגון |

### תכונות ⁦BGP⁩ – ארבע שנשאלות

| ⁦Attribute⁩ | תפקיד | הערה |
|---|---|---|
| **⁦AS-PATH⁩** | רשימת ה-⁦AS⁩-ים בדרך. **מונע לולאות.** קצר יותר = עדיף. | חובה |
| **⁦Next-Hop⁩** | הכתובת שאליה שולחים | חובה |
| **⁦Local Preference** | **"⁩מאיזה נתב לצאת מה-⁦AS"⁩** – גבוה = עדיף. רק בתוך ה-⁦AS. | "⁩קובע את נקודת היציאה" |
| **⁦MED** | "⁩לספק: תיכנס אליי דרך הנתב הזה" – נמוך = עדיף. נשלח ל-⁦AS⁩ **שכן**. | "⁦Multi-Exit Discriminator"⁩ |
| **⁦Weight⁩** | של ⁦Cisco⁩ בלבד, מקומי לנתב, גבוה = עדיף. נבדק **ראשון**. | לא עובר לאף אחד |

**סדר הבחירה** (מקוצר): ⁦Weight⁩ → ⁦Local Preference⁩ → ⁦AS-PATH⁩ הקצר → ⁦MED⁩ הנמוך → ⁦eBGP⁩ לפני ⁦iBGP.⁩

### הגדרה – סניף מול ספק

```
! Branch edge router, AS 65001, peering with ISP AS 65010
Router(config)# router bgp 65001
Router(config-router)# bgp router-id 1.1.1.1
Router(config-router)# neighbor 200.100.1.1 remote-as 65010
Router(config-router)# network 200.100.1.0 mask 255.255.255.0
```

| שורה | למה |
|---|---|
| `⁦router bgp 65001⁩` | ה-⁦ASN⁩ **שלנו**. ⁦64512⁩–⁦65534⁩ = טווח פרטי (כמו ⁦10.x⁩ בכתובות). |
| `⁦neighbor X remote-as 65010⁩` | "השכן ב-⁦X⁩ שייך ל-⁦AS 65010".⁩ שונה משלנו → **⁦eBGP**.⁩ |
| `⁦network ... mask ...⁩` | **מה לפרסם החוצה.** שימו לב: **הכתובת הציבורית**, לא ⁦10.x.⁩ |

`⁦show ip bgp summary⁩` – השכנים ומצבם (**⁦State = Established⁩** = טוב; מספר בעמודה = מספר נתיבים שהתקבלו). `⁦show ip bgp⁩` – **"טבלת הניתוב של ⁦BGP"⁩** שבנק השאלות מבקש.

## ⁦7.5⁩ מה הסניף מפרסם ומה לא – הדרישה החשובה

דרישה ⁦22.17: **"⁩ניתוב אל מחוץ לסניף לכיוון ה-⁦WAN⁩ יהיה סטטי ולא באמצעות פרוטוקול ניתוב (יש להימנע מלהעביר מידע ניתובי על פנים הרשת לרשת העולמית)."**

התרגום: **אסור** לעשות `⁦redistribute ospf⁩` לתוך ⁦BGP.⁩ אם עושים – כל ה-⁦10.1.16.0/24, 10.1.17.0/24...⁩ של הארגון מגיעים לטבלה של הספק. הספק לא יעביר אותם (כתובות פרטיות), אבל הוא **יראה** את מבנה הרשת הפנימית שלכם. מידע לתוקף.

מה **כן**: ב-⁦BGP⁩ מפרסמים **רק את הכתובות הציבוריות** (`⁦network 200.100.1.0⁩`). והרשת הפנימית מגיעה החוצה דרך **⁦NAT⁩**, לא דרך ניתוב.

## ⁦7.6⁩ הסתירה לכאורה – ⁦BGP⁩ או סטטי?

| דרישה | אומרת |
|---|---|
| **⁦3** | "⁩פרוטוקול הניתוב ב-⁦WAN⁩ יהיה ⁦BGP"⁩ |
| **⁦22.17** | "⁩ניתוב אל מחוץ לסניף יהיה סטטי" |

תלמידים חושבים שזו סתירה. **זו לא.** אלה **שתי שיחות שונות**, בין **מכשירים שונים**:

<div dir="ltr" align="left">

```
   inside the branch              edge router                carrier
   (DIST switches, core)          (R-TLV-EDGE1)              (AS 65010)
          |                            |                          |
          |   ip route 0.0.0.0 0.0.0.0 -----> "everything else,   |
          |   STATIC default            |     that way"           |
          |                            |                          |
          |                            |   eBGP session --------->|
          |                            |   advertises 200.100.1.0 |
          |                            |   learns the world       |
          |                            |                          |
   private 10.x lives HERE  --NAT-->   public 200.100.x lives HERE

   The IGP (OSPF) never crosses the edge router.  BGP never enters the branch.
   The edge router is where the two worlds meet - and it translates between them.
```

</div>

- **בתוך הסניף → נתב הקצה:** נתיב ברירת מחדל **סטטי**. הסניף צריך עובדה אחת: "לא שלי → לשם". (דרישה ⁦22.17⁩ ✓)
- **נתב הקצה ↔ הספק:** **⁦eBGP**.⁩ מפרסם רק ציבורי, לומד את העולם. (דרישה ⁦3⁩ ✓)
- **בין סניפים, כתובות פרטיות:** דרך **⁦VPN⁩** מעל ה-⁦WAN⁩ (חלק ⁦2⁩, פרק ⁦8). BGP⁩ נושא רק ציבורי; ⁦10.x⁩ לא נכנס לספק בכלל. (דרישה ⁦2⁩ ✓ – "⁦VPN⁩ כדי לאפשר תקשורת בין כתובות ⁦IP⁩ פרטיות")

**ברגע שרואים את דרישה ⁦2⁩ כפתרון לסתירה ולא כדרישה נפרדת – כל תכנון ה-⁦WAN⁩ מסתדר.**

## ⁦7.7 DNS⁩ – מה קורה כשמקלידים כתובת

הכול עד עכשיו עבד עם מספרים. אבל אתם מקלידים `⁦google.com⁩`, לא ⁦142.250.1.1. **DNS (Domain Name System)⁩** מתרגם. שכבה ⁦7, **UDP⁩ פורט ⁦53** (TCP 53⁩ לתשובות גדולות ולהעברת אזורים).

<div dir="ltr" align="left">

```
You type:  www.nimbus.local

  1. PC checks its cache.  Not there.
  2. PC asks its DNS server (from DHCP: 10.1.200.53):   "www.nimbus.local?"
  3. Server checks its records.  Finds:   www.nimbus.local  A  10.1.200.80
  4. Server answers.  PC caches it (for the record's TTL).
  5. Only NOW does the PC send the HTTP request - to 10.1.200.80.

  If the server does not know (google.com):
  3'. It asks the ISP's DNS -> which asks the root servers -> .com -> google's servers.
      This is RECURSION.  The answer comes back down the chain and is cached at every step.
```

</div>

**סוגי רשומות** (נשאלים):

| רשומה | ממפה | דוגמה |
|---|---|---|
| **⁦A⁩** | שם → כתובת ⁦IPv4⁩ | `⁦www.nimbus.local⁩ → ⁦10.1.200.80⁩` |
| **⁦AAAA⁩** | שם → כתובת ⁦IPv6⁩ | `⁦www⁩ → ⁦2001:db8:3::80⁩` |
| **⁦CNAME⁩** | שם → שם אחר (כינוי) | `⁦mail.nimbus.local⁩ → ⁦srv1.nimbus.local⁩` |
| **⁦MX⁩** | דומיין → שרת דואר | `⁦nimbus.local⁩ → ⁦mail.nimbus.local⁩` |
| **⁦PTR⁩** | כתובת → שם (הפוך) | `⁦10.1.200.80⁩ → ⁦www.nimbus.local⁩` |
| **⁦NS⁩** | דומיין → שרת השמות שלו | |

**בפרויקט:** שרת ⁦DNS⁩ ב-⁦DMZ⁩ של תל אביב (⁦10.1.200.53)⁩ עם רשומות לשרתים הפנימיים, ושרת ⁦DNS⁩ אצל ה-⁦ISP⁩ לאורחים ולעולם. **"בשביל מה שרת ⁦DNS⁩ ובאיזה פורט?"** – תרגום שמות, ⁦53.⁩

> 🔐 **מבט קדימה**
>
> ⁦DNS⁩ הוא יעד תקיפה קלאסי: **⁦DNS Spoofing / Cache Poisoning⁩** – תוקף מזריק תשובה שקרית ("⁦google.com⁩ זה ⁦6.6.6.6")⁩ והדפדפן מגיע לאתר מזויף. **⁦DNS Tunneling⁩** – הברחת מידע החוצה בתוך שאילתות ⁦DNS⁩, כי פורט ⁦53⁩ כמעט תמיד פתוח. שניהם בחלק ⁦2⁩, פרק ⁦1.⁩

## ⁦7.9⁩ סיכום

⁦1.⁩ פרטי לא יוצא. **⁦NAT⁩** מחליף פרטי ↔ ציבורי. ⁦Inside Local / Inside Global / Outside Global.⁩
⁦2.⁩ **סטטי** ⁦1:1⁩ קבוע, לשרת נגיש מבחוץ (תל אביב). **דינמי** ממאגר (חיפה). **⁦Overload/PAT⁩** לפי פורט, הכול דרך כתובת אחת (באר שבע).
⁦3.⁩ `⁦ip nat inside⁩` / `⁦outside⁩` על הממשקים – **חובה**, הטעות הראשונה לבדוק.
⁦4. NAT⁩ הוא לא חומת אש.
⁦5. **AS⁩** = רשתות בניהול אחד. ⁦IGP⁩ בפנים (⁦OSPF/EIGRP), EGP⁩ בין (⁦BGP).⁩
⁦6. BGP: TCP 179⁩, שכנים ידניים, ⁦Path Vector. **AS-PATH⁩ מונע לולאות. ⁦Local Pref⁩ = נקודת יציאה. ⁦MED⁩ = לספק "תיכנס כאן". ⁦Weight = Cisco⁩, מקומי.** ⁦eBGP AD 20, iBGP 200.⁩
⁦7.⁩ **מפרסמים ב-⁦BGP⁩ רק ציבורי. לעולם לא ⁦redistribute⁩ של ה-⁦IGP.⁩** בתוך הסניף – סטטי לקצה. פרטי בין סניפים – ⁦VPN.⁩
⁦8. DNS⁩: שכבה ⁦7, UDP 53. A / AAAA / CNAME / MX / PTR.⁩ רקורסיה.

**תרגיל ⁦1.⁩** מחשב ⁦192.168.1.50⁩ גולש דרך נתב עם ⁦PAT⁩ על ⁦85.64.1.1.⁩ הוא פותח ⁦3⁩ חיבורים. כתבו איך תיראה טבלת ה-⁦NAT⁩ (בערך), והסבירו איך הנתב יודע לאיזה מחשב להחזיר כל תשובה.

</details>

**תרגיל ⁦2.** NAT⁩ דינמי מוגדר נכון (מאגר, ⁦ACL⁩, פקודת ⁦nat).⁩ אף מחשב לא מצליח לגלוש. `⁦show ip nat translations⁩` ריק. מה הבדיקה הראשונה?

<details><summary>פתרון</summary>

`⁦ip nat inside⁩` ו-`⁦ip nat outside⁩` על הממשקים. בלי הם, ⁦NAT⁩ מוגדר אבל לא **מופעל** על שום ממשק – טבלה ריקה, שום תרגום. `⁦show ip nat statistics⁩` מציג "⁦Inside interfaces:"⁩ ו-"⁦Outside interfaces:"⁩ – אם ריק, זו הבעיה.

</details>

**תרגיל ⁦3.⁩** שרת ⁦WEB⁩ פנימי ב-⁦10.1.200.80⁩ צריך להיות נגיש מהאינטרנט בכתובת ⁦200.100.1.80.⁩ איזה סוג ⁦NAT⁩? כתבו את הפקודה. למה ⁦PAT⁩ לא מתאים כאן?

<details><summary>פתרון</summary>

**סטטי:** `⁦ip nat inside source static 10.1.200.80 200.100.1.80⁩`. ⁦PAT⁩ לא מתאים כי ב-⁦PAT⁩ אין שורה בטבלה עד שהמחשב הפנימי **יוזם** – ומבקר מבחוץ לא יכול ליזום לשרת. סטטי יוצר שורה קבועה, שני הכיוונים.

</details>

**תרגיל ⁦4.⁩** נתב ב-⁦AS 65001⁩ מקבל נתיב עם ⁦AS-PATH⁩: `⁦65010 65020 65001 65030⁩`. מה יעשה איתו ולמה?

<details><summary>פתרון</summary>

**יזרוק אותו.** ה-⁦ASN⁩ שלו (⁦65001)⁩ מופיע ב-⁦AS-PATH⁩ – הנתיב כבר עבר דרכו. לקבל אותו = לולאה. זה מנגנון מניעת הלולאות של ⁦BGP.⁩

</details>

**תרגיל ⁦5.⁩** לארגון שני נתבי קצה, שניהם ב-⁦eBGP⁩ לספקים שונים. רוצים שכל התעבורה **תצא** דרך נתב ⁦A.⁩ איזו תכונה מגדירים, על מי, ובאיזה ערך?

<details><summary>פתרון</summary>

**⁦Local Preference⁩** – "נקודת היציאה מה-⁦AS".⁩ מגדירים על נתב ⁦A⁩ ערך **גבוה** (למשל ⁦200⁩; ברירת מחדל ⁦100). Local Pref⁩ מופץ ב-⁦iBGP⁩ בתוך ה-⁦AS⁩, אז נתב ⁦B⁩ ילמד שהיציאה דרך ⁦A⁩ עדיפה. (⁦MED⁩ היה משפיע על **כניסה** מהספק, לא על יציאה.)

</details>

**תרגיל ⁦6.⁩** מנהל מוסיף `⁦redistribute ospf 1⁩` לתוך ⁦BGP⁩ בנתב הקצה "כדי שהכול יעבוד". איזו דרישה בפרויקט הופרה, ומה הסיכון?

<details><summary>פתרון</summary>

דרישה **⁦22.17**.⁩ כל רשתות ה-⁦10.x⁩ הפנימיות נשלחות לספק. הוא לא ינתב אותן (פרטיות), אבל **ידע את מבנה הרשת הפנימית** – ⁦VLAN⁩-ים, סניפים, גדלים. מידע מודיעיני לתוקף. הדרך הנכונה: `⁦network⁩` רק לציבורי, ו-⁦NAT⁩ לפנימי.

</details>

**תרגיל ⁦7.⁩** מחשב מצליח לעשות `⁦ping 142.250.1.1⁩` אבל `⁦ping google.com⁩` נכשל. איפה הבעיה? ומה אם ההפך?

<details><summary>פתרון</summary>

פינג ל-⁦IP⁩ עובד → ניתוב ו-⁦NAT⁩ תקינים. פינג לשם נכשל → **⁦DNS⁩**: המחשב לא מצליח לתרגם. לבדוק `⁦ipconfig /all⁩` (איזה ⁦DNS⁩ קיבל), ואם השרת נגיש (פורט ⁦53).⁩ **ההפך** – שם עובד, ⁦IP⁩ נכשל – כמעט בלתי אפשרי, כי פתרון השם מייצר את אותו ⁦IP⁩; אם קרה, כנראה ה-⁦DNS⁩ החזיר כתובת אחרת (⁦cache⁩ ישן או ⁦spoofing).⁩

</details>

## 📝 שאלות בסגנון בחינה

**שאלה ⁦1.⁩** הסבירו מהו ⁦NAT⁩ ומדוע הוא נחוץ. השוו בין שלושת סוגי ה-⁦NAT⁩: לכל אחד – מתי משתמשים, מה המגבלה, ופקודת ההגדרה.

<details><summary>תשובה לדוגמה</summary>

**⁦NAT⁩** – תרגום כתובות בנתב הקצה: בדרך החוצה מחליף כתובת מקור **פרטית** (⁦10.x)⁩ ב**ציבורית**; בדרך חזרה מחליף בחזרה לפי טבלה. **למה נחוץ:** נתבי האינטרנט לא מעבירים כתובות פרטיות, ותשובה ל-⁦10.1.16.40⁩ לא תגיע לעולם (יש מיליוני כאלה). גם: מחסור בכתובות ציבוריות.

| | סטטי | דינמי | ⁦Overload / PAT⁩ |
|---|---|---|---|
| מתי | שרת שצריך להיות **נגיש מבחוץ** (⁦WEB)⁩ | כמה מחשבים, מאגר ציבורי | הכול דרך כתובת **אחת** |
| יחס | ⁦1:1⁩ קבוע, שני כיוונים | ⁦1:1⁩ זמני ממאגר | רבים:⁦1⁩ לפי **פורט** |
| מגבלה | כתובת ציבורית לכל שרת | מחשב ⁦n+1⁩ מחכה כשהמאגר גמור | אין יזום מבחוץ |
| פקודה | `⁦ip nat inside source static 10.1.200.80 200.100.1.80⁩` | `⁦ip nat pool P 200.100.2.10 200.100.2.29 netmask ...⁩` + `⁦access-list 1 permit ...⁩` + `⁦ip nat inside source list 1 pool P⁩` | `⁦access-list 1 permit ...⁩` + `⁦ip nat inside source list 1 interface Gi0/1 overload⁩` |

**בכולם:** `⁦ip nat inside⁩` / `⁦ip nat outside⁩` על הממשקים – חובה.

</details>
**שאלה ⁦2.⁩** מהי מערכת אוטונומית? הסבירו את ההבדל בין ⁦IGP⁩ ל-⁦EGP⁩, ומדוע האינטרנט זקוק לפרוטוקול מסוג ⁦EGP.⁩

<details><summary>תשובה לדוגמה</summary>

**מערכת אוטונומית (⁦AS)⁩:** אוסף רשתות תחת **ניהול אחד** עם **מדיניות ניתוב אחת** – ארגון, ספק, גוגל. לכל ⁦AS⁩ מספר (⁦ASN).⁩ האינטרנט = עשרות אלפי ⁦AS⁩-ים שמדברים זה עם זה.
**⁦IGP (Interior)⁩** – ⁦OSPF, EIGRP⁩ – **בתוך** ⁦AS.⁩ מטרה: הדרך **המהירה** ביותר. סומך על כל הנתבים (כולם שלנו). **⁦EGP (Exterior)⁩** – ⁦BGP⁩ – **בין** ⁦AS⁩-ים. מטרה: הדרך **המותרת לפי מדיניות** – עסקית, חוזית, ביטחונית. סומך רק על השכן הישיר, ובזהירות.
**למה צריך ⁦EGP:** (1)⁩ **קנה מידה** – ⁦OSPF⁩ לא יכול להחזיק מפה של מיליון רשתות ולהריץ ⁦SPF⁩ על כולה. (⁦2)⁩ **מדיניות** – ספק לא רוצה "הדרך הקצרה"; הוא רוצה "דרך השותף שלי, לא דרך המתחרה", גם אם ארוכה יותר. ⁦IGP⁩ לא יודע לבטא את זה. (⁦3)⁩ **אמון** – בתוך הארגון סומכים על כל נתב; בין ארגונים לא. ⁦BGP⁩ בנוי לאי-אמון: שכנים ידניים, סינון, מדיניות.

</details>
**שאלה ⁦3.⁩** תארו ארבע תכונות של ⁦BGP⁩ ואת תפקידה של כל אחת. מהו ההבדל בין ⁦eBGP⁩ ל-⁦iBGP⁩?

<details><summary>תשובה לדוגמה</summary>

**⁦AS-PATH⁩** – רשימת ה-⁦AS⁩-ים שהנתיב עבר. **מונע לולאות**: נתב שרואה את ה-⁦ASN⁩ שלו ברשימה זורק את הנתיב. קצר יותר = עדיף. **⁦Next-Hop⁩** – הכתובת שאליה שולחים. **⁦Local Preference⁩** – "**מאיזה נתב לצאת** מה-⁦AS"⁩ – גבוה = עדיף, מופץ ב-⁦iBGP⁩ בתוך ה-⁦AS⁩ בלבד. **⁦MED⁩** – רמז ל-⁦AS⁩ **השכן** "תיכנס אליי דרך הנתב הזה" – נמוך = עדיף. **⁦Weight⁩** – ⁦Cisco⁩ בלבד, מקומי לנתב, לא עובר לאף אחד, גבוה = עדיף, נבדק **ראשון**.
**סדר בחירה:** ⁦Weight⁩ → ⁦Local Pref⁩ → ⁦AS-PATH⁩ הקצר → ⁦MED⁩ הנמוך → ⁦eBGP⁩ לפני ⁦iBGP.⁩
**⁦eBGP⁩** – בין **שני ⁦AS⁩-ים שונים** (הסניף ↔ הספק). ⁦AD **20**.⁩ השכנים בדרך כלל מחוברים ישירות. **⁦iBGP⁩** – בין **שני נתבים באותו ⁦AS⁩** (שני נתבי הקצה של הארגון). ⁦AD **200**. iBGP⁩ לא מפיץ הלאה נתיב שלמד מ-⁦iBGP⁩ אחר (כדי למנוע לולאות – לכן צריך ⁦Full Mesh⁩ או ⁦Route Reflector).⁩

</details>
**שאלה ⁦4.⁩** בפרויקט נדרש שהניתוב ב-⁦WAN⁩ יהיה ⁦BGP⁩ וגם שהניתוב מהסניף החוצה יהיה סטטי. הסבירו כיצד שתי הדרישות מתקיימות יחד, ומדוע אסור להפיץ את ה-⁦IGP⁩ לתוך ⁦BGP.⁩

<details><summary>תשובה לדוגמה</summary>

**שתי שיחות, שני מכשירים:** (⁦1)⁩ **בתוך הסניף → נתב הקצה:** נתיב ברירת מחדל **סטטי** (`⁦ip route 0.0.0.0 0.0.0.0⁩ <edge>`). הסניף צריך עובדה אחת – "לא שלי → לשם" (דרישה ⁦22.17⁩ ✓). (⁦2)⁩ **נתב הקצה ↔ הספק:** **⁦eBGP**.⁩ מפרסם רק את הכתובות **הציבוריות** (`⁦network 200.100.1.0⁩`), לומד את העולם (דרישה ⁦3⁩ ✓). ה-⁦IGP (OSPF)⁩ לעולם לא חוצה את נתב הקצה; ⁦BGP⁩ לעולם לא נכנס לסניף. (⁦3)⁩ **בין סניפים, כתובות פרטיות:** דרך **⁦VPN⁩** מעל ה-⁦WAN⁩ – ⁦BGP⁩ נושא רק ציבורי, ⁦10.x⁩ לא נכנס לספק (דרישה ⁦2⁩ ✓).
**למה אסור ⁦redistribute⁩:** `⁦redistribute ospf⁩` לתוך ⁦BGP⁩ שולח את **כל** רשתות ⁦10.x⁩ הפנימיות לספק. הוא לא ינתב אותן (פרטיות), אבל **יראה את מבנה הרשת הפנימית** – כמה ⁦VLAN⁩-ים, אילו סניפים, גדלים. מידע מודיעיני לתוקף, וגם עומס מיותר. הרשת הפנימית מגיעה החוצה דרך **⁦NAT⁩**, לא דרך ניתוב.

</details>
**שאלה ⁦5.⁩** תארו את תהליך פתרון השם כאשר משתמש מקליד כתובת אתר. ציינו את סוגי הרשומות העיקריים ואת הפורט שבו ⁦DNS⁩ פועל.

<details><summary>תשובה לדוגמה</summary>

**התהליך:** (⁦1)⁩ המשתמש מקליד `⁦www.nimbus.local⁩`. (⁦2)⁩ המחשב בודק **מטמון** מקומי. (⁦3)⁩ לא נמצא → שולח שאילתה (⁦UDP⁩, פורט **⁦53**)⁩ לשרת ה-⁦DNS⁩ שקיבל מ-⁦DHCP. (4)⁩ השרת בודק את הרשומות שלו – אם יש **רשומת ⁦A⁩** – עונה. (⁦5)⁩ אם אין (למשל ⁦google.com)⁩ – **רקורסיה**: שואל שרת ברמה גבוהה יותר (הספק → ⁦Root⁩ → .⁦com⁩ → השרת של ⁦google)⁩, התשובה חוזרת בשרשרת ונשמרת במטמון בכל שלב. (⁦6)⁩ רק **עכשיו** המחשב שולח את בקשת ה-⁦HTTP⁩ לכתובת שקיבל.
**רשומות:** **⁦A⁩** – שם → ⁦IPv4. **AAAA⁩** – שם → ⁦IPv6. **CNAME⁩** – שם → שם אחר (כינוי). **⁦MX⁩** – דומיין → שרת דואר. **⁦PTR⁩** – כתובת → שם (הפוך). **⁦NS⁩** – דומיין → שרת השמות שלו.
**פורט:** **⁦UDP 53⁩** לשאילתות רגילות; ⁦TCP 53⁩ לתשובות גדולות ולהעברת אזורים בין שרתים.
